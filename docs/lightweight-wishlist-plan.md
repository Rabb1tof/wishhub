# План облегчения WishHub и редактируемых карточек

Дата: 30 октября 2026. Статус: план реализации, прикладной код ещё не изменён.
Ветка плана: `chore/lightweight-wishlist-plan`.
Исходная версия: `ea05ec00798251fe6678d3886c7d91b8c4ed3c7d` (`origin/main` на момент подготовки).

Этот документ задаёт актуальный порядок работы для облегчения проекта. Прежние пункты о развитии Playwright, stealth, обязательном image proxy, мониторинге цен и расширении браузера в [plan.md](../plan.md) сохраняются как история и не являются заданиями этой реализации.

## 1. Требуемый результат

Пользователь вставляет ссылку, по желанию нажимает **«Получить данные»**, проверяет и редактирует карточку, затем сохраняет её. Единственные обязательные поля — **ссылка и имя**. Получение данных помогает заполнить форму, но не является условием сохранения.

| Поле | Правило |
|---|---|
| Ссылка | Обязательный абсолютный HTTP(S) URL, после Trim, максимум 2000 символов. Поддержка магазина источником метаданных не требуется для ручного сохранения |
| Имя | Обязательная непустая строка после Trim, максимум 500 символов. Пользователь может изменить полученное имя |
| Фото | Необязательная ссылка или файл JPEG/PNG/WebP до 5 МиБ с превью; можно заменить и удалить. Отсутствующая или недоступная картинка не блокирует сохранение |
| Цена | Необязательное nullable-число. Можно ввести, исправить и очистить. Отрицательная цена недопустима; ноль отличается от отсутствующей цены |
| Валюта | Значение по умолчанию RUB; отдельным обязательным действием пользователя не является |

Обязательные свойства новой логики:

- Нет Playwright, Chromium, Selenium/WebDriver, Puppeteer, CloakBrowser/CDP, browser pools и браузерных fallback в приложении, зависимостях и образах.
- Нет фонового парсинга, регулярного обновления цен, многоминутных повторов и постоянного опроса статуса карточки.
- Внешний запрос метаданных выполняется только по кнопке. Вставка ссылки, сохранение, открытие списка и редактирование полей его не запускают.
- Сохранение URL + имени работает при отключённом внешнем интернете, при ошибке источника и для неизвестного магазина.
- Все пользовательские значения принадлежат конкретной записи вишлиста. Правки одного владельца не меняют чужие карточки того же товара.
- Сценарий одинаков для сайта и будущего Telegram Mini App: без расширений, bookmarklet и действий на странице магазина.
- Используются бесплатные возможности. Никаких автоматических покупок квоты, платного продления и обхода CAPTCHA.

## 2. Поведение формы

1. Форма сразу позволяет ввести URL, имя, фото и цену вручную. Кнопка сохранения зависит только от валидности обязательных полей и введённых необязательных значений.
2. «Получить данные» доступна при корректном URL. На время запроса она показывает локальную загрузку и защищена от повторных нажатий.
3. Успешный ответ предлагает имя и одно основное фото. Цена может остаться пустой: отдельный сбор цен в этой работе не разрабатывается.
4. Полученные значения заполняют пустые, не изменённые вручную поля. Ручные изменения, в том числе сделанные во время запроса, не затираются. Для замены уже заполненных значений нужна явная команда пользователя «Применить найденное».
5. Изменение URL отменяет либо инвалидирует текущий запрос. Ответ для ссылки A не применяется к форме со ссылкой B. Неподтверждённые автоматические значения для прежней ссылки сбрасываются; ручные значения сохраняются.
6. При таймауте, отсутствии результата, квоте или неизвестном источнике форма остаётся редактируемой. Сообщение объясняет, что данные не получены и их можно заполнить вручную. Новые фоновые попытки не создаются.
7. После сохранения доступны редактирование ссылки, имени, фото, цены и удаление необязательных значений. Повторный сбор снова заполняет форму и сам по себе ничего не сохраняет.
8. Карточка без фото использует аккуратную заглушку; без цены — состояние «Цена не указана», без бесконечного spinner. Состояния загрузки и ошибок не переносятся в долговременную модель товара.

Реальная форма сейчас находится в `frontend/src/pages/WishlistPage.tsx` (`AddItemModal` внутри страницы). Изменение только `components/AddWishlistItemModal.tsx` не исправит пользовательский сценарий. Карточки также отображаются в `ProfilePage.tsx` и `FeedPage.tsx`.

## 3. Минимальная архитектура

### Получение данных

Один авторизованный endpoint, например `POST /api/metadata/resolve`, принимает `{ url }` и возвращает необязательные `name`, `imageUrl`, а также результат `ok | partial | unavailable | unsupported` и короткую понятную причину при необходимости. Он не создаёт `Product`, `WishlistItem`, уведомления или задания.

Оставить существующий небольшой модуль `WishHub.Parsing` и упростить его контракт до получения необязательных метаданных. Переиспользовать имеющуюся фабрику выбора источника. Не вводить отдельный микросервис, очередь, workflow engine или новую универсальную систему плагинов.

Для первичной реализации выбрать серверное выполнение адаптеров: один контракт для веба и Mini App, ключи остаются на сервере. Прямой CORS-fetch WB из клиента уже проверен экспериментально, но дублировать адаптер между клиентом и сервером ради него не нужно. Возможность клиентского выполнения можно оценить позже при подтверждённой необходимости.

Стартовые ограничения, проверяемые перед выпуском:

- Общий deadline одного действия — 12 секунд, включая дополнительные попытки и переходы; отмена при отключении запроса.
- Один целевой источник; для Маркета допустима одна необязательная попытка поискового API. Нет каскада из многих сервисов и фоновых повторов.
- Не более трёх проверяемых редиректов; не более 1 МиБ метаданных и пяти кандидатов картинки в ответе. Изображения целиком для разбора метаданных не скачиваются.
- Ограничение частоты запросов по пользователю и ограничение общей параллельности. При 429 возвращается редактируемая форма, а не скрытое ожидание очереди.
- Для повторных публичных ссылок допустим ограниченный `IMemoryCache` с TTL. Хранить только небольшие результаты, не HTML, картинки и ручные поля пользователя. Redis для этого не требуется.
- Проверять URL через `Uri`, точный hostname и структуру пути. Не использовать `Contains("ozon.ru")` и поиск произвольного числа во всей строке.
- Для исходящих запросов проверять схему, публичные IP/DNS и каждый редирект; закрыть localhost/private/link-local адреса и встроенные credentials. Host из внешней карты CDN также проверяется. Не передавать сторонним сервисам cookies и токены пользователя.
- Отбрасывать CAPTCHA, страницы ошибок, общие названия магазина, логотипы и неверные SKU даже при HTTP 200. Неполный ответ допустим и не должен превращаться в успешную полную карточку.

### Сохранение и изменение

`POST /api/wishlist` и `PUT /api/wishlist/{id}` получают итоговые значения формы. Они не вызывают адаптеры и не скачивают фото. Для полного обновления `ImageUrl: null` и `Price: null` означают очистку, а не «оставить прежнее». Порядок сортировки не сбрасывается при редактировании содержимого.

В API и frontend синхронно перейти к собственным полям карточки `Url`, `Name`, `ImageUrl?`, `Price?`, `Currency`, `Source`. Отказаться от обязательной вложенности `ProductDto` и processing-полей. Ошибки аутентификации, доступа и валидации отделять от отсутствия внешних метаданных.

### Изображения

Самый лёгкий целевой вариант — nullable URL картинки в карточке и обычный `<img>` в клиенте с `loading="lazy"`, `referrerPolicy="no-referrer"` и обработкой ошибки. URL можно заменить или очистить. Для внешних фото допускаются HTTP(S) URL; для собственных файлов — только строгий внутренний путь /api/wishlist-images/{owner}/{file}. Значения выводятся как данные, без вставки HTML.

Это позволяет удалить `ImageProxyController`, Redis и хранение картинок в Redis. Браузер пользователя делает обычную загрузку изображения с CDN; сервер WishHub не запускает для этого браузер. Возможные hotlink-ограничения источника дают заглушку и редактирование, а не отказ сохранения.

По дополнительному запросу пользователя загрузка собственного файла входит в этот этап. Файл необязателен: JPEG/PNG/WebP до 5 МиБ; проверка сигнатуры, случайное имя, ограниченная потоковая запись, без декодирования/серверных превью/новых image-библиотек. Хранилище вне wwwroot, постоянный volume wishlist_images. API выдаёт файл с проверкой видимости вишлиста; владелец видит свой черновик, другие — только привязанное к доступной карточке фото. На одного владельца 100 МиБ, неиспользуемые файлы старше 24 часов убираются при очередной загрузке. Форма показывает предпросмотр/ошибку, позволяет заменить или убрать файл; сохранение не теряет незавершённую загрузку молча. Существующие аватары сохраняются отдельно.

Перед изменением frontend обновить правило раздела Images в `AGENTS.md`, которое сейчас требует `/api/images/proxy`; привести DTO и документацию к выбранной новой схеме.

Для Ozon перед включением в релиз проверить доступность из реального окружения WishHub, фактические лимиты и допустимость бесплатной интеграции WBRay. Лимит скачивания фото в интерфейсе не равен лимиту запросов метаданных. Если устойчивый бесплатный способ не подтверждён, оставить автоматическое заполнение Ozon экспериментальным/отключаемым; ручное добавление остаётся полноценным. Подключение платного источника не является автоматическим резервом.

Для Google/Маркета:

- Хранить ключ только на backend; без ключа или при исчерпании квоты возвращать `unavailable` без блокировки сохранения.
- Проверять страницу-источник результата, hostname, product ID и явно выбранный вариант; первую похожую фотографию автоматически не принимать.
- Если несколько подходящих результатов неразличимы, предложить выбор или ручное фото. Не обращаться к карточке Маркета браузером для дополнительной проверки.
- Не парсить HTML Google и не использовать скрытый Search Element для сбора и постоянного хранения выдачи. Проверить условия выбранного поискового API и работу именно его image endpoint.
- Короткие share-URL требуют отдельной проверки безопасного разрешения: непрозрачный токен нельзя превратить в артикул локальной регуляркой. Неразрешённая короткая ссылка всё равно сохраняется вручную.

Источники исследования: [WBRay](https://wbray.ru/ozon/photo-download/), [Shopify Product API](https://shopify.dev/docs/api/ajax/reference/product), [WooCommerce Store API](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/products/), [Google Images API SerpApi](https://serpapi.com/google-images-api), [Google Search Element](https://developers.google.com/custom-search/docs/element). Условия и поддержка внешних сервисов проверяются повторно при реализации; опубликованный тариф не считается успешным тестом товара.

## 5. Хранение и миграция существующих карточек

Целевая модель — самодостаточный `WishlistItem`: URL, имя, фото, цена, валюта и источник рядом с существующими владельцем, порядком и резервацией. Общая изменяемая сущность `Product` больше не определяет пользовательские поля. Глобальный кеш метаданных, если нужен, не является авторитетной карточкой пользователя.

Переход выполнить новыми миграциями, не переписывая исторические:

1. Добавить поля карточки и перенести значения из связанных Products, сохранив `WishlistItem.Id`, `OwnerId`, `CreatedAt`, `SortOrder`, резервации и связи пользователей. В этой же первой миграции сделать прежний `ProductId` nullable: новые самостоятельные записи его не заполняют, исторические связи остаются до отдельной очистки. Старые Products не удалять и не запускать каскадное удаление связанных карточек.
2. Имя переносить по приоритету: непустой `CustomName` → нормальное `Product.Name` → понятное временное имя по домену для старых пустых/«Загрузка...» записей. Подсчитать такие замены в отчёте миграции. Новые карточки пустое имя не принимают.
3. Фото и цену копировать в каждую запись отдельно, сохраняя null. Миграция не ходит в интернет и не запускает повторный сбор данных.
4. Все Pending/Processing/Failed становятся обычными доступными для редактирования карточками. Старые parsing-ошибки не удерживают UI в загрузке.
5. Перевести чтение, фильтры, сортировку и запись на поля `WishlistItem`. Зафиксировать положение карточек без цены при сортировке; при активном ценовом фильтре null-цена не удовлетворяет диапазону. Сохранить запрет дубля одного нормализованного URL внутри одного вишлиста, но разрешать тот же URL разным владельцам. При редактировании исключать текущую запись из проверки дубля; конфликт возвращать без изменения прежних данных. При совпадениях в старых данных ничего не удалять автоматически; сначала отчёт и разрешение коллизий.
6. Старые Products/FK/колонки убрать отдельной миграцией только после проверки переноса и резервной копии. Приложение к этому моменту от них не зависит. Историческую схему Hangfire и старые volumes не стирать автоматически.

Нормализация URL начинается с Trim и нормализации схемы/hostname; регистр пути не менять. Сохранять параметры выбранного товара/варианта (`sku`, `variant` и подобные). Удалять только известные tracking-параметры по явному правилу источника; неизвестные query-параметры и значимые fragment сохранять. Отбрасывание всей query string и объединение разных вариантов в один товар недопустимы.

У миграций должны быть корректные `Down`, но обратная общая модель не представляет независимые ручные значения нескольких пользователей. После новых правок нельзя обещать безопасный откат только командой Down: необходимы резервная копия, проверенный порядок восстановления и защита новых данных от потери. Деструктивная очистка откладывается до закрытия этого условия.

## 8. Критерии приёмки

### Поведение и данные

- [ ] URL + имя без фото и цены сохраняются, в том числе без доступа к интернету и без попытки получить метаданные.
- [ ] Пустое/пробельное имя, недопустимая схема URL и отрицательная введённая цена отклоняются; цена 0 и отсутствие цены различаются.
- [ ] Неизвестный магазин, 403/CAPTCHA, 429, таймаут, отсутствие ключа и пустая выдача не блокируют ручное сохранение.
- [ ] Фото/цена изменяются и очищаются; битая картинка не ломает карточку и не запускает повторный сбор.
- [ ] Только кнопка инициирует сбор; POST/PUT сохранения, GET списка и загрузка профиля не вызывают источники.
- [ ] Поздний ответ для прежней ссылки игнорируется; ручные правки во время запроса сохраняются; предложенные данные применяются без автоматического сохранения.
- [ ] Два владельца с одинаковым URL могут иметь разные имя/фото/цену. Правка/удаление одной карточки не меняет другую.
- [ ] Старые Pending/Failed записи доступны для чтения и редактирования; сохранены ID, порядок, резервации, доступ к приватным вишлистам и сокрытие резерва от владельца.

### Источники и лёгкость

- [ ] WB проверен на нескольких разных категориях, вариантах и CDN-маршрутах; неизвестный формат карты завершается мягким отказом, без перебора хостов.
- [ ] Ozon проверен на действующих разных товарах из окружения развертывания; общие страницы/посторонние фото отвергаются. Доступность источника не подменяется обещанием поддержки всей площадки.
- [ ] Для Маркета Google считается реализованным только после теста реального API с бесплатным ключом; похожий товар с другим ID не принимается за точное совпадение.
- [ ] Исходящие обращения проверены на подмену hostname, private IP, опасный редирект, чрезмерный ответ и неверную схему URL. Ограничения времени/частоты соблюдаются.
- [ ] В активном коде, пакетах, scripts, CI и Docker отсутствуют браузерные зависимости/установки/процессы и слушающий CDP. Исторические документы и миграции не считаются runtime-зависимостью.
- [ ] Приложение запускается и сохраняет карточку с PostgreSQL без Redis и Hangfire; в idle нет обращений к источникам товаров.
- [ ] Обязательные автоматические проверки используют сохранённые HTTP-ответы/локальные handlers и не зависят от маркетплейсов или CAPTCHA. Живые smoke-пробы запускаются отдельно, по явной необходимости.
- [ ] Форма проверена на мобильном размере экрана. Фактическая работа внутри Telegram WebView квалифицируется отдельно при реализации Mini App.

## 9. Граница готовности этого документа

Документ описывает будущие изменения и критерии, а не выполненную миграцию. Ветка плана не удаляет зависимости, не меняет БД, не публикует образы и не развёртывает приложение. WB/Ozon имеют подтверждённые рабочие примеры лёгкого получения данных; Google для Маркета остаётся условным дополнительным источником. Надёжность создания карточки обеспечивается независимым ручным сохранением обязательных URL и имени.
