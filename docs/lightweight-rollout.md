# Переход на редактируемые карточки

API и frontend этой версии изменяют контракт карточек: обязательны URL+Name, фото и цена nullable; Product больше не владеет пользовательским содержимым. Промежуточные версии разных веток не разворачиваются по отдельности.

## Перед запуском

1. Сделайте и проверьте резервную копию PostgreSQL, сохраните аватары и volume загруженных фото wishlist_images, если он уже есть. Зафиксируйте текущую версию образов для восстановления.
2. Остановите старые API workers и recurring scheduling до приёма ручных правок. Уже поставленные старые задания не должны перезаписать данные и не должны исполняться новым приложением.
3. Проверьте новую миграцию на копии данных: количество и ID карточек, owner, sortOrder, резервации, CustomName/названия, null фото/цены. Миграция не требует доступа к магазинам.
4. Новые поля заполняются из legacy Product, ProductId становится nullable. Новые карточки не создают Product. Исторические таблицы/связи сохраняются до отдельной безопасной очистки; прежние миграции не переписываются.

## Обновление

Запускайте совместимые API и frontend с PostgreSQL. API применяет миграции при старте. Новый состав Compose исключает Redis/browser services и их runtime mounts, сохраняя pgdata и avatars и подключая wishlist_images к /app/App_Data/wishlist-images. Файлы находятся вне wwwroot, доступ проверяет API. Внешний ingress должен пропускать multipart до 6 МиБ; API ограничивает сам файл 5 МиБ. Не выполняйте удаление volumes пользовательских данных.

Проверьте загрузку JPEG/PNG/WebP, сохранение карточки с фото, замену/очистку фото, доступ владельца/друга/постороннего и сохранность файла после пересоздания API. Для резервного копирования согласованно сохраняйте PostgreSQL и wishlist_images. Для одного экземпляра API лимит составляет 100 МиБ на владельца; при загрузке удаляются не привязанные к карточкам файлы старше 24 часов. Не удаляйте каталог фото при обычном обновлении.

После запуска проверьте `/health`, вход, ручное создание карточки с URL+именем при недоступном внешнем интернете, изменение/очистку необязательных полей, две независимые карточки одного URL у разных владельцев, приватность и резервирование. Метаданные запрашиваются только кнопкой; у Ozon это экспериментальный opt-in.

## Откат

Наличие метода Down не означает безопасный откат бизнес-данных: прежний общий Product не представляет разные ручные значения владельцев и новые записи без ProductId. После таких изменений используйте проверенный сценарий восстановления с сохранением новых данных; не запускайте автоматический откат схемы, который их теряет. Деструктивную очистку legacy-таблиц делайте отдельно после проверки перехода и резервной копии.
